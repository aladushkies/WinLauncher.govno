## 1. L‑01 — ограниченная очередь и слияние снапшотов

`RootBridge.send()` получил пятый параметр `mergeable` и различает два вида coalescing:

* **mergeable** (снапшот `tasks`) — старый запрос **передаёт свои callback'и** новому.
  Отправляется один запрос, но ответ получают все, кто к нему присоединился;
* **не-mergeable** (resize) — старое поведение сохранено без изменений: superseded-запрос
  получает ровно `"superseded by newer resize"`, и `WindowController` по-прежнему считает
  эту ошибку безобидной (`H‑03`).

Ключ coalescing у `tasks` — `"tasks"`, поэтому в очереди может лежать **не более одного**
неотправленного снапшота.

Граница очереди — `MAX_PENDING_REQUESTS = 64`. Когда очередь заполнена, из неё удаляется
**самый старый mergeable-запрос**, и его callback'и получают
`"dropped: request queue full"`. Если mergeable-запросов нет (очередь забита
пользовательскими resize), новый запрос отклоняется с `"request queue full"` —
пользовательская команда не вытесняется снапшотом. Отклонённый запрос отвечает
**всем** присоединившимся к нему, а не только своему первому caller'у.

Важно: `MAX_PENDING_REQUESTS` — это страховка, а не основной механизм. Обычный путь
(опрос раз в 750 мс) держит в очереди ровно один снапшот.

## 2. L‑02 — `close()` отвечает ожидающим

`RootBridge.close()` больше не выбрасывает очередь молча:

```java
ArrayDeque<Request> pending;
synchronized (lock) { pending = new ArrayDeque<>(queue); queue.clear(); }
for (Request request : pending) deliverAll(request, error("bridge closed"));
```

Раньше вызывающий, ждавший ответа (обновление списка задач, resize), **никогда** не
получал результата: callback просто исчезал вместе с очередью. Для `TaskManagerActivity`
это означало навсегда застывший статус, для `WindowController` — потерянное уведомление
об ошибке.

---

## 3. L‑03 — мёртвая idle-сессия отбрасывается до записи

`RootServer` закрывает сессию, которая простояла без запросов 120 с
(`socket.setSoTimeout(120000)`). `LocalSocket` при этом может продолжать рапортовать
`isConnected() == true`, и команда, записанная в такой сокет, пропадает. Команды с
побочным эффектом (`resize`, `stack`, `close`, `device`, `status`) автоматически не
повторяются — то есть такая потеря была необратимой.

Клиент теперь запоминает время последней записи (`lastIoAt`) и при превышении
`SESSION_IDLE_TIMEOUT_MS = 120000` рвёт сокет и переподключается **до** отправки команды.
Значение константы совпадает с серверным таймаутом, и это закреплено проверкой L‑03.

## 4. L‑04 — не более одного снапшота в полёте

`WindowController.refreshTasks()` теперь держит флаг `snapshotInFlight`:

* если снапшот уже выполняется, новый вызывающий **присоединяется** к нему
  (`snapshotWaiters`) и получает ответ того же запроса;
* флаг сбрасывается **до** `adoptTasks()`, поэтому refresh, вызванный из обработки
  ответа, не теряется.

Раньше каждый тик опроса порождал отдельный запрос `tasks`, даже если предыдущий ещё
не ответил; медленный RootServer накапливал по запросу на тик.

---

## 5. L‑05 — `virtual_hidden_tasks` пишется только при изменении

`reconcileVirtualDesktopVisibility()` больше не пишет скрытое множество в prefs на каждом
опросе. Запись выполняется только если множество действительно изменилось:

```java
if(!hidden.equals(prefs.virtualDesktopHiddenTasks()))prefs.setVirtualDesktopHiddenTasks(hidden);
```

Тот же guard-паттерн, что уже использовался в `moveWindowToDesktop()` (`hiddenChanged`).
Проверка L‑05 требует, чтобы в теле метода осталась **ровно одна** запись — и именно
в таком виде.

## 6. L‑06 — владение активным контроллером

Статическая регистрация `WindowController.activeController` писалась **только** в
конструкторе. Отсюда две проблемы:

1. Контроллер, переживший пересоздание Activity (retained-экземпляр `DockService`),
   не мог восстановить регистрацию, а статические потребители —
   `KeyService` (горячие клавиши), `ActionCenterOverlay` (верхний inset),
   `LauncherSettingsActivity` — молча получали «контроллера нет».
2. `MainActivity.ensureController()` начинался с
   `if (controller != null && windowsListener != null) return;` — из-за этого
   существовавший ниже rebind на живой контроллер сервиса был **недостижим**. Если
   `DockService` перезапускался и создавал новый контроллер, Activity продолжала держать
   старый (с уже закрытым bridge) и не узнавала о новом.

Изменения:

| Место | Изменение |
|---|---|
| `WindowController` | Поле `released`; `releaseActive()` ставит его и снимает регистрацию |
| `WindowController` | Новый `claimActive()` — владелец переутверждает регистрацию, если контроллер не освобождён |
| `DockService.keepAlive()` | Вызывает `controller.claimActive()` — сервис владеет и контроллером, и регистрацией |
| `MainActivity.ensureController()` | Определяет `stale` (сервис заменил контроллер), снимает listener/error-listener со старого и перепривязывается к живому; в rebind-ветке тоже вызывается `claimActive()` |

`WindowController.active()` остаётся источником истины для `KeyService`,
`ActionCenterOverlay` и `LauncherSettingsActivity`; `TaskManagerActivity` по-прежнему
предпочитает `DockService.controller()` и только затем обращается к `active()`.

## 8. Что осталось непроверенным

* **Gradle/AGP-сборка и D8 не выполнялись** — в окружении нет Android SDK/Gradle.
* **APK не собран, устройство SM‑T555 не подключалось.** Runtime-приёмка обязательна:
  проверить, что при подвисании RootServer опрос действительно прекращает накапливать
  запросы, что resize после 2 минут простоя проходит с первой попытки, что Task Manager
  и статусная строка не залипают при закрытии сервиса.
* Не измерено на устройстве реальное потребление памяти до и после ограничения очереди —
  оценка сделана по коду (один снапшот вместо N неотправленных).
* Сценарий «`DockService` перезапущен системой, `MainActivity` жив» воспроизводится только
  вручную (kill сервиса по нехватке памяти), в автоматических проверках он не покрыт.
